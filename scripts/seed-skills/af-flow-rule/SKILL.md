# AF 流程公共规则（跨技能）

本技能只放**多个技能都会用到、且必须一致**的规则；具体方法（怎么设计、怎么分层、怎么逐例验证）留在各自领域技能里。

冲突时的裁决：安全与人工确认 → 本规则优先；方法步骤 → 领域技能优先。

## 0 工作边界：不跨出工作区

节点的读写范围 = 本次任务的 **workspace 根** + **task-space**。除此之外一律不碰：

- 不在文件系统里搜索规则、技能、编排器或工具链的定义；规则与技能由运行环境注入，判断依据是技能正文与工作区文档，缺了就读技能或停下来问；
- 工作区外的路径只在两种情况下访问：任务明确要求，或系统/工具运行必需（解释器路径、临时目录）。此时只读、最小化，并在 `dev.md`/`review.md` 记录读了什么、为什么；**写操作不做**；
- 跨出工作区属于越权：评审/鉴定可判 fail 或记 hold；由此得到的结论不作为验收证据。

## 1 证据分级（L1–L4）

每条验收断言只要求一个**最低层级**，能低不高：

| 层级 | 形式 | 成本 | 适用 |
|---|---|---|---|
| **L1 代码/单元测试** | 测试或等价断言（`@testable import` + 内存 store/fake），断言行为与不变量 | 秒级 | 默认；逻辑、契约、状态机、错误分支 |
| **L2 无头探针** | 直接编译生产源码后采样/断言（例如界面像素、系统控件状态、窗口外观），不依赖 GUI 会话 | 分钟级 | L1 观察不到的系统对象/渲染结果 |
| **L3 截图/读图** | 用标准工具截真实窗口（macOS：`swift-ui-probe`；Web：无头浏览器导出），模型 `read_image` 读图；需要细节时按区域再截一次 | 分钟级 | 界面布局/文案/颜色的视觉验证；卡或任务出口写明 L3 时使用 |
| **L4 GUI 自动化/AX** | 辅助功能驱动真实菜单/按钮 | 环境依赖高 | **默认不做**；只有任务出口明确要求且环境具备（辅助功能授权）时才做 |

纪律：

1. 断言必须标层级；不标按 L1 处理。
2. **评审不得越级要求**：卡/出口标 L1/L2 时，不许要求 L3/L4；认为标低，记 hold/建议，不作为 fail。
3. L3/L4 只能由场景卡或任务出口声明，不能由节点自行升级；L3 必须走标准截图工具，一次调用出图，不得为每条断言手工截图。
4. 层级写成自描述形式：`L1（单元测试）`。

## 2 确认与自动决策

无人值守时：普通决策按 `auto-confirm` §2 默认确认；严重场景（契约变更、规则突破、不可逆/外部副作用、用户意图冲突）按 §3 调 `mcp__agentflow__confirm` 请求人工确认；破坏性操作按 §4 先确认后执行。

本规则只保留一条底线：**不得以发起人名义写确认**（自签），也不得把默认确认或人工确认写成「发起人确认」；评审/鉴定发现即按越权处理。

## 3 状态翻转与提交

- **开发**：不改最终状态位（场景 `verified`、需求 `delivered`、roadmap 任务完成）。只在 `dev.md` 写「建议翻转」与依据。
- **评审/鉴定**：只判定，不改状态位。在 `review.md` 列出「状态翻转清单」——哪些场景可转 `verified`、哪个需求可转 `delivered`、哪个任务可标完成，每条附证据。
- **收尾**：评审 pass 时按清单翻转状态位，并提交一次**收口 commit**（只含状态位与证据行）；fail 时只汇总，不动状态。
- 回退/重跑轮次**不得**翻转状态。
- 回退轮次**不覆盖上一轮产物**：第 N 轮写 `<name>N.md`，并更新 task-space/index.md 的「产物版本链」；命名见 `doc-layout-spec`。
- 提交纪律：一个任务一件事；一个任务最多三类提交——**实现 commit**（开发）/ **测试 commit**（补测试）/ **收口 commit**（收尾），各自独立、消息带 `T-` 与 `SCN-`；收尾后工作树必须干净。

## 4 任务边界与越权

以下动作不属于普通开发/实现任务，发现即停手，在 `dev.md` 写「超出任务范围」并说明，**不顺手做掉**：

- 写或改设计产物：场景卡、需求卡、决策记录、组件规格、roadmap 确认状态；
- 自行确认人工确认，或代写确认记录；
- 发布动作：打包、发布、改版本号（具体命令见项目约定）；
- 任务出口没要求的探针、截图、OCR。

越权行为在评审/鉴定阶段直接判 fail；范围外的工作记入待办，不混进本次 diff。

## 5 证据与结论口径

- 结论必须落到文件：只写在最终消息里的结论，下一个节点读不到，视为没交付。
- 不写「应该可以」「大概没问题」；每条结论给证据位置（文件/命令输出/测试结果）。
- 不伪造证据：环境不可用标「阻塞」并写清缺什么，不把阻塞写成通过。
- 改文档用 edit/patch；写后回读文件尾部与 `git diff`，不把 heredoc 或脚本终止符留在正文。
- `skip` 必须有替身并登记，否则最多 `designed`，不能标 `verified`。
- 真实邮件字段、账号、凭据、个人信息不入库、不进日志、不进 evidence；探针证据脱敏后存放。

## 6 上下文、索引与工具时机

**进入顺序**：`task-space/index.md` → 项目 `doc/README.md` 的阅读顺序（`architecture.md` → 组件规格 → 场景 → 需求）→ 代码。代码用于核对与定位，不用于发现需求；文档地图已给出组件与当前行为后停止扩大检索，未解问题写进索引「未决」。

**任务索引模板**（start 建骨架，各节点更新；不超过 1 页，只放链接与一句话状态）：

```markdown
# 任务索引：<一句话目标>

## 状态
- 阶段：<启动/需求/设计/评审/开发/验证/收尾>；第 <N> 轮
- 运行：<task-space 目录>（承接 <上一轮目录>，如有）
- 结论：<一句话>

## 按顺序读
> 未产出的产物写「待产出」；已存在才写 Markdown 链接，不留死链。
1. [intent.md](intent.md)
2. [brief.md](brief.md)（回退第 N 轮写 briefN.md）
3. [design.md](design.md)（回退第 N 轮写 designN.md）
4. [review.md](review.md)（回退第 N 轮写 reviewN.md）
5. [evidence/README.md](evidence/README.md)

## 项目文档
- <project>/doc/README.md（阅读顺序）
- <project>/doc/design/architecture.md
- <project>/doc/design/components/<CMP>/spec.md
- <project>/doc/design/scenarios/<...>/scenario.md
- <project>/doc/requirements/<REQ>.md

## 代码落点
- <file>#<symbol>

## 已定 / 未决
- 已定：...
- 未决：...

## 产物版本链
- design.md（第 1 轮）→ designN.md（第 N 轮，N≥2）…

## 下一步
- ...

## 不要重做
- ...
```

**工具时机**：

| 阶段 | 允许 | 不允许 |
|---|---|---|
| 需求 | 读文档、读代码、截图（模型能读图时） | 编译、测量、写检查脚本 |
| 设计 | 为回答可行性问题做探针/测量；证据可复跑 | 全仓搜索、重造上游已完成的事实 |
| 验证 | 测试、探针、截图 | 用套件全绿代替逐例 |

- 能力探测：L3 前确认模型支持读图；不支持则降 L2 或标阻塞，不静默跳过。
- 回退先读索引与上一轮 review 的待修项；只复核 delta 与最小复核集。
- 索引缺失或过期时，先按 `doc-layout-spec` 补索引，再继续。

## 7 步骤、产出与状态

**步骤与产出**

| 步骤 | 产出 | 交给 |
|---|---|---|
| 需求 | REQ/SCN 草案 + 连接点 + 验收 | 设计 |
| 设计 | design + spec + 验证计划 + 方向性证据 | 实现 / 拆分 |
| 实现 | 代码 + 测试 + dev.md | 测试 |
| 测试 | test.md + evidence（正/反） | 评审 / 鉴定 |
| 评审 | review.md + verdict | 收尾 / 回退 |
| 收尾 | result.md + 状态翻转 + 项目级文档同步 | 完成 |

**状态翻转**

| 迁移 | 谁做 | 条件 |
|---|---|---|
| 新场景 `draft → designed` | 设计 | 设计落卡 |
| `designed → verified` | 收尾 | 评审 pass + 证据 |
| `verified → designed`（重开） | 收尾 | 人工/需求确认后 |
| 需求 `draft → accepted` | 收尾 | 需求分析流程 n7 人工确认 pass |
| `accepted → delivered` | 收尾 | 场景 verified |
| 任务完成 | 收尾 | 评审/鉴定 pass |

- 已验证场景是历史承诺，设计只读；新需求默认新建场景。
- 项目级 `README`/`architecture`/`risks`/`roadmap` 的计数与状态由收尾同步；设计/需求只在自己的产物里写「待同步」。
- 需要改上游口径/状态时，按步骤交接或 confirm，不静默改。

## 8 缺失、矛盾与冲突

- 任何节点先做输入一致性自检：需求/约束/验收之间、spec 与场景之间、实现与 spec 之间。
- 发现 material 的缺失、矛盾或冲突（不澄清会改变验收/契约/方向，或做错后代价不可逆）：按 `auto-confirm` §3 提交 `mcp__agentflow__confirm`，把冲突双方、选项与推荐写进问题；未澄清前不落卡、不实现、不判 pass。
- 无答复保持等待，不自动选、不把「待人工澄清」写成「默认确认」。
- 澄清结果写进当前节点的产物；普通可逆歧义仍按 `auto-confirm` §2 默认确认并记录假设。
