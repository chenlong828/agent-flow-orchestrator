# 用途

测试节点之后、收口之前使用。回答一个问题：**这次实现是否真正走完**——不是「代码写完没有」，而是「场景卡里的每条例子都有可复核的通过证据」。

输入：场景卡 3 正 1 反、`test.md` 与 `evidence/`、`dev.md`（实现 commit 与测试记录）、实现提交本身。
输出：`task-space/review.md`（逐项核验证据）+ 最终消息最后一行裸 JSON verdict。

## 核验步骤

1. **范围**：确认本次只做了 intent 指定的任务，提交只含该任务「允许改的范围」内的改动；越界直接 fail（工作区边界见 `af-flow-rule` §0，越权清单见 §4）。
2. **逐例核对**：场景卡每条例子在 `test.md` 里都有结果；通过的要有可复核证据（`evidence/` 里的命令输出或断言片段），缺证据的按未通过处理。
3. **反向核对**：拒绝清单里的「未覆盖」「阻塞」「跳过」——这些不能算通过，必须在 `test.md` 里说明，并在结论里体现。
4. **回归**：依赖场景的既有用例仍绿；有退化直接 fail。
5. **证据层级**：按任务出口与场景卡标注核对，不越级要求（分级规则见 `af-flow-rule` §1；卡标 L1/L2 时不要求截图或 AX）。
6. **提交卫生**：实现 commit 存在且消息带 `T-` 与 `SCN-`；若补了测试，测试 commit 单独存在且只含 `Tests/`；没有把状态位提前翻转；工作树干净。一个任务最多三类提交：实现 / 测试 / 收口，各一件事。
7. **判定**：
   - 全部满足 → `pass`；
   - 任一不满足 → `fail`，`reason` 必须写清：回退到哪个实现节点、改什么、怎么复现（命令/输入/实际输出）。

## verdict 输出

最后一行一个裸 JSON 对象，不加代码围栏，其后不再写内容：

{"verdict":"pass","reason":"3 正 1 反逐条有证据，依赖场景无回归，提交干净"}

{"verdict":"fail","reason":"回实现节点：T-SCN-0007-04 的畸形地址用例未补，test.md 标未覆盖；复现：<项目测试命令> --filter <用例>"}

## 不该做的

- 替开发改代码、补测试或修文档。
- 默认放行：证据缺失时按未通过处理，不猜、不补脑。
- 把「全量测试绿」当成「例子全过」。
- fail 却不给回退目标与复现步骤（回退后开发无从下手）。
- 翻转场景/需求状态（状态翻转归收尾）。
