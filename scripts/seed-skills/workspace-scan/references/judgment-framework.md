# 通用判断框架（语言无关）

机器规则之外，评审的判断项按同一组维度组织；每个检查方案在自己的 `references/judgment-checklist.md` 里把这些维度落到该语言的判据与证据形式。工作区只定义维度，不写具体技术规则。

## 六个维度

| 维度 | 回答的问题 | 证据形式 |
|---|---|---|
| 结构与依赖 | 职责是否单一？依赖方向是否向下？跨模块是否只走契约？ | 组件地图、import 清单、架构测试结果 |
| 契约与数据 | 契约是否完整？数据是否只有一个写入口？事务与幂等是否成立？ | 契约卡、schema diff、迁移、并发测试 |
| 错误与边界 | 失败路径谁负责？是否吞错？输入校验是否在边界？ | 失败注入测试、错误码、日志样例 |
| 安全与运行边界 | 密钥、鉴权、越权、路径/注入是否受控？ | 校验点、权限测试、脱敏证据 |
| 异步与资源 | 超时、取消、背压、连接释放是否成立？ | 压测/超时测试、指标 |
| 测试与改动卫生 | 断言是否有效？diff 是否聚焦？证据是否可复核？ | 测试输出、report JSON、commit 记录 |

## 使用方式

1. 先跑该方案的机器检查，拿到 `check-report@1`。
2. 按六个维度逐项写「查了什么 / 结论 / 证据位置」；没有证据的“已检查”不算。
3. 机器规则覆盖的项可以直接引用报告；判断项不能拿报告里的 PASS 代替。
4. 结论分 pass / fail / 有条件通过；fail 必须给可执行的回退点。

## 与具体方案的关系

- `js-backend-code-review` 提供 JS 后端的判据与证据要求。
- 未来 Java/Rust/Vue 方案各自提供同结构的清单；维度保持一致，判据按语言替换。
- 若某方案缺判断清单，视为该方案未完成，不能只靠机器规则通过评审。
