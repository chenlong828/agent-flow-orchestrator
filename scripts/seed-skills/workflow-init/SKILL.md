# 用途

工作流的第一个节点使用。把本次运行的诉求落成文件，并建立 task-space 的导航索引与 brief 骨架，让后续节点先读索引、按索引读产物与项目文档，而不是各自从提示词或全仓搜索猜。

## 步骤

1. 从「运行环境」块读取 `task-space` 路径与「启动诉求」原文。
2. 确认 task-space 目录存在且可写；不存在时创建。
3. 把诉求原文写入 `<task-space>/intent.md`：不改写、不摘要、不补充。
4. 按 `af-flow-rule` §6 的「任务索引」模板建立 `<task-space>/index.md` 骨架：目标（链接 intent.md）、阶段=启动、必读顺序、项目文档/代码落点待填、下一步=需求分析；把 `brief.md` 一行写成「骨架（待需求节点填写）」的链接。
5. 按下面的骨架创建 `<task-space>/brief.md`：只写结构与占位，**不摘要诉求、不写范围/验收结论**；`module`、`updated` 等元数据留待需求节点填。
6. 在最终消息里报告三个文件路径与 intent 字节数。

```markdown
---

module: 待需求节点填写
scope: run
status: active
updated: <YYYY-MM-DD>
---
```

## 完成标准

- `intent.md` 存在，内容与诉求原文一致（首尾空白除外）。
- `index.md` 存在、不超过 1 页、链接可解析，且没有业务结论；`brief.md` 一行指向骨架。
- `brief.md` 存在，包含上述 8 节与占位；没有诉求摘要、范围/验收/设计结论。
- 没有在 task-space 之外创建或修改文件。

## 常见踩坑

- 把诉求「总结成一句」再写，导致后续节点拿到的不是原文。
- 把索引写成需求/设计结论；索引只做导航与当前状态。
- 把 `brief.md` 骨架写成范围、验收或设计结论；骨架只写结构与占位。
- 顺手创建 `scenario-drafts.md`、`design.md`、`review.md` 等后续节点才该产出的文件。
