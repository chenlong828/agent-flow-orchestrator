# 阈值与基线：为什么是这些数

阈值不是自然常数，是“先用数据选一条能产生反馈的线”，再靠 ratchet 收敛。默认值来自一个真实 JS 后端仓库（2026-10）的分布；项目应在管理态用自己仓库的分布校准，而不是照搬。

## 默认值的来历

- **文件 600 行**：当时分布 >300 有 8 个、>400 有 6 个、>500 有 5 个、>600 有 1 个。600 只卡住最大的一个，作为新文件绝对上限；500 是提醒线，覆盖 4 个中大型文件。
- **函数 80 行**：分布 >80 有 19 个、>100 有 16 个、>120 有 12 个。80 对应“一屏能读完”的维护单位；选 100 会少抓 3 个，选 120 会少抓 7 个。
- **复杂度 15、参数 5、嵌套 4**：与函数行数一起看；复杂度高不是靠拆行能解决的，拆行只是让问题可见。
- **扇出 8**：超过 8 通常说明在越权编排；组合根单独豁免。
- **克隆块 8 行 / 70 tokens**：低于这个粒度的 helper 副本是检测盲区，不强行纳入。

## 校准纪律

1. 先跑 `report`，看实测值，不先改阈值。
2. 只为“规则不适用”或“确实需要放宽”调阈值，且必须带：改前实测、改后阈值、理由、影响面。
3. 存量问题进 `baseline`，只降不升；新增问题必须修，不能进基线。
4. 规则集升级用 `adopt`，逐条决定启用或豁免，不静默变更级别。
5. 同一仓库两次运行结果不一致时，先查工具版本与缓存，不要调阈值。

## 常见误用

- 为了让门禁变绿，把 HARD 改成 WARN 或把阈值调高。
- 把“当前值”写死成阈值，导致规则失去约束力。
- 用 baseline 吸收新增问题，基线越滚越大。
- 在不同平台用不同工具版本，报告不可比。
