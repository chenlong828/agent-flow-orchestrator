# 用途

AF 默认**无人值守**，但不是"所有事都自动拍板"。本技能把确认分成三条通道：

1. **默认确认**（自动）：普通、可逆、在已 accepted 范围内的决策；记录「未经人工」，继续。
2. **应急人工确认**（MCP）：严重、会改变契约/规则/方向/不可逆的决策；调用 `mcp__agentflow__confirm`，任务暂停，等人在 UI 答复后带 `[人工确认]` 继续。
3. **停手不执行**：破坏性/外部副作用；只有明确人工同意才执行，否则停。

## 1 先判断通道

| 情形 | 通道 | 行为 |
|---|---|---|
| 流程里有 `confirm` 节点，或人明确在环 | `confirm` 节点 / 人 | 按节点/人答复；不自动跳过 |
| 普通决策（§2） | 默认确认 | 自动，记录假设，继续 |
| 严重场景（§3） | MCP 应急确认 | 调 `mcp__agentflow__confirm`；暂停；按 `[人工确认]` 继续 |
| 破坏性/外部副作用（§4） | 先确认，再执行 | 只有明确 `pass` 才执行；否则停 |
| 无人应答 | 阻塞 | 不推进、不伪造、不写成通过 |

`run.autoConfirm` 只控制流程图里 `confirm` 节点的自动通过，不关闭 agent 节点的 MCP 应急确认；严重场景仍可提问。

## 2 默认确认：不打断人

适用范围：

- P3；P2 中不触碰契约/schema/数据所有权/兼容性/不可逆的局部改动；
- 已 accepted 需求/场景范围内的实现细节（命名、结构、参数、文档归属、格式）；
- 同一方案族内的参数选择（**方案族本身**属于 §3 的严重决策）；
- 有推荐项/默认项的技术选择。

做法：

- 按推荐/默认执行；
- 记录「默认确认：D1–D8（无人值守自动确认，依据 `<文件>` §…；**未经人工**）」；
- 写进 `history/decisions/` 同样标注「未经人工」；
- **用户意图默认**：涉及"用户要什么效果、验收口径、非目标"的默认，标「假设（未经人工）」并写回退；不得把用户原话里的示例数字自动升级为硬契约；验收与用户价值冲突时，按用户原话的效果执行并记录假设；
- **禁止**写成「发起人确认」「已确认（人签字）」——那是自签；
- 有一个以上合理解读且代价相当 → 不是普通决策，走 §3。

## 3 应急人工确认（MCP）：只给严重场景

只有以下情形调用 `mcp__agentflow__confirm`：

1. **契约变更**：改已 accepted 的需求口径/场景验收、公共契约、schema、跨模块接口、数据所有权、状态机，或撤销既有不变量（行高/布局承诺等）。
2. **规则突破**：违反 AGENTS/技能硬规则、越过任务边界（写别人的文件、翻状态位、越权）、需要跳过质量门/证据层级。
3. **范围/代价**：新增用户未提的非目标/约束、跨项目/团队、不可逆迁移、高爆炸半径、新增依赖/权限/付费。
4. **用户意图冲突**：两种合理解读且代价相当；验收与价值冲突；示例数字要不要升级为契约；范围是否扩大。
5. **关键信息缺失**：无法从文档/代码/已确认记录推断，继续会做错方向。
6. **P0/P1 决策**：需要人参与设计/共同决策的级别。

**不要用于**：普通参数、命名、文档归属、可逆实现选择、已有明确人工确认的同一问题、为了"确认一下"推进流程。

提问规则：

- 一次一个问题；2–4 个选项；推荐项放第一个；必要时允许自由文本（`allowFreeText`）。
- `question` 短；`context` 写清：现状、为什么现在必须决定、选项、推荐、影响、不回答的后果、回退方式。
- 字段上限：`question` ≤2048、`context` ≤8192、`options` ≤8 条且每条 ≤200。
- 调用后本轮结束，不再执行其他工具、不再提交；任务进入 `waiting_confirm`，UI 显示待确认。
- 等待期间不推进、不假设通过、不伪造答复。

收到 `[人工确认]` 后：

- `pass`：按选项/意见执行；记录「人工确认：<问题>；决定 pass；意见 …」；
- `reject`：按拒绝意见调整，不重复被拒方案；若仍阻塞，最多再问一个更窄的问题；
- 自由文本与选项冲突时，以文本为准；
- 同一问题不重复问；只有新证据/新范围才可以再问。

## 4 停手与执行授权

- 删除/覆盖工作区、`git reset --hard`、`git clean`、发布、真实外发、账号/权限/付费：先走 §3 确认；只有明确 `pass` 才执行。
- 没有答复就停；不执行、不假设同意、不写成通过。
- 环境/工具无法执行时，报告阻塞；不伪造。

## 5 与评审/确认节点的关系

- `confirm` 节点按节点机制等待 `pass`/`reject`；`agent` 节点用 `resultSignal=confirmation_request` 的 `mcp__agentflow__confirm`。
- `review` 节点同时挂 `signal` 与 `confirm` 两个工具：**只允许**在「必须澄清已 accepted 需求/契约口径，且该口径直接决定 verdict」时呼人；评审判断本身不外包。
- 评审确认的边界：
  - 允许：已 accepted 卡有两种合理解读且直接改变 verdict；设计与上游 accepted 卡冲突、需要人定哪边权威；证据只能由人提供且缺它无法判定。
  - 禁止：问「这个方案好不好」「该 pass 还是 fail」；用 confirm 代替 verdict、代替证据、代替回退；同一问题重复问；一次访问超过 1 个问题。
  - `pass`/`reject` 都只作评审输入，不是 verdict；回答后评审仍须自行调用 `mcp__agentflow__signal` 提交 `review_verdict`。
  - 无答复时 run 保持 `waiting_confirm`，不自动 pass；取消后评审不写「已通过」。
- 评审不是人工确认的替代；评审 `pass` 不代表契约变更已获人同意。
- 评审无法确认的契约问题仍可按 `fail` 回退，由上游 agent 在下一轮用 §3 提问。
- 默认确认与人工确认都不得写成「发起人确认」。

## 6 记录格式

- 默认：「默认确认：D1–D8（无人值守自动确认，依据 …；未经人工）；回退：…」
- 人工：「人工确认：<问题>；决定：pass/reject；意见：…；节点/时间：…」
- 未答：「阻塞：等待人工确认（问题 …）；未执行 …」
- `history/decisions/` 区分「默认确认（未经人工）」与「人工确认」。
