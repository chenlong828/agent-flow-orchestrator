# 用途

测试节点使用。验证单元是**场景卡里的例子**，不是「再跑一遍全量套件」。输出一份逐例对照表，让后续的实现鉴定能按证据判断实现是否走完。

输入：场景卡（本次改动对应的 SCN，见 `doc/design/scenarios/`）、`intent.md`、`dev.md`、组件规格。
输出：`task-space/test.md`（逐例对照表 + 回归结果 + 未覆盖/阻塞项）与 `task-space/evidence/`（命令输出、断言片段）。

## 步骤

1. **锁定场景**：从 intent 与 dev.md 找出本次改动对应的 SCN；列出它的依赖场景（场景卡「不可变引用」里点到的）。
2. **建逐例清单**：场景卡「测试」表每条一行——ID、正/反、输入、期望、可执行测试（有则填，没有标「待补」）。
3. **补测试并提交**：例子没有可执行测试时，只改 `Tests/`，遵守项目测试框架与命名；不改产品代码；补完把测试 ID 回填清单。
   补完测试后提交一个**独立的测试 commit**（只含 `Tests/` 与必要的测试 fixture）：
   - message 形如 `test(reply-all): cover T-SCN-0007-04 malformed addresses (T-1114-09, SCN-0007)`；
   - 不与实现 commit 混在一起；提交后 `git status` 干净，收尾才有干净工作树；
   - 本次没有补测试就不产生测试 commit。
4. **执行**：按清单逐条跑对应测试（先 `--filter` 到相关 suite，再跑全量兜底）；涉及 UI 或网关的例子跑冒烟——用 CLI/AX + 本地录制网关，**不向真实收件人投递**，记录完整命令。
5. **判定每条**：通过 / 失败 / 阻塞（环境不可用，写明缺什么）。不要用「套件全绿」代替「逐条例子通过」。
6. **回归**：依赖场景的既有用例必须仍绿；把回归命令与结果写进 `test.md`。
7. **产出**：`test.md` 用一张表覆盖全部例子；证据落 `evidence/`，`test.md` 引用文件名。

## 判定口径

- 3+1 逐条有结果、依赖场景无回归 → 交实现鉴定。
- 任一条失败 → 写清复现步骤（命令、输入、实际输出），交回开发。
- 环境不可用 → 标「阻塞」并写清需要什么环境；不猜、不伪造、不把阻塞写成通过。

## 不该做的

- 只跑全量套件，拿「套件全绿」交差。
- 例子缺测试就跳过，或只在报告里写「未覆盖」。
- 改产品代码去让测试通过（只允许补 `Tests/`）。
- 把补写的测试留在工作树里不提交，让后面的节点或收尾去收拾。
- 冒烟时向真实邮箱投递，或把真实邮件字段、凭据写进仓库。
- 把 `SCN` 标 `verified`（状态翻转归收尾）。
