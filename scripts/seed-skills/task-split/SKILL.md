# 用途

设计完成之后、开发开始之前使用。回答两件事：这次改动要拆成几个可独立交付的任务、每个任务什么时候算完成。

输入：需求卡（`doc/requirements/`）、场景卡（`doc/design/scenarios/`）、组件规格（`doc/design/components/<id>/spec.md`）、方案/架构评审结论、现状代码（只读）。

输出：任务表（ID/类型/组件/依赖/状态/出口）+ 并行关系 + 装载清单，写进项目 `doc/plan/roadmap.md` 的批次任务表。task-space 只留本次拆分的记录，不存唯一副本。

## 拆分步骤

1. **识别改动面**：逐个组件列出要动的契约、数据结构、视图或接线，每条指向组件规格的具体段落；指不到说明设计不足。
2. **切任务**：一个任务 = 一次可提交、可独立验证的改动。跨两个组件、需要两次独立验证的，拆开。
3. **定依赖**：按数据 → 领域 → 适配 → 存储 → 场景 → 视图 → 接线的方向排；共享公共契约的必须串行。
4. **定出口**：写清跑哪条测试、看哪个文件、哪条命令输出、留什么证据。出口不能是「完成实现」「功能可用」这类无法验证的表述。
5. **排并行**：确认无依赖才标可并行；同一组件或同一契约上的任务一律串行（组件级 WIP=1）。
6. **落表**：写进项目 `doc/plan/roadmap.md` 的批次任务表；任务 ID 在工作区内稳定不复用。

## 任务表格式

| 任务 | 类型 | 组件 | 依赖 | 状态 | 出口 |
|---|---|---|---|---|---|
| `T-xxxx-01` | design / change / verify | `CMP-xxx` | 前序任务 ID | 待启动 / 进行中 / 已完成 | 可检查的验收证据 |

表下补两行：可并行关系；本批的统一验证命令（如 `./Scripts/xxx test`、架构门脚本）。

## 一个任务成立的判据

- 能指到组件规格的具体段落，不是「大概要动一下这里」；
- 出口可检查：有测试名 / 命令 / 文件 / 证据位置；
- 依赖无环，且没有跨组件的隐式耦合；
- 粒度 = 一次可提交的改动；实现、补测试、状态收口可以各自一次提交（都带 `T-` 与 `SCN-`），但不拆成多次实现提交；
- 装载可完成：单任务需读的文件量在预算内（超了就再拆）。

## 不该做的

- 在需求阶段拆任务：设计未定，拆出来的是猜测。
- 按文件拆、按工时拆；任务边界应跟着契约与验收走。
- 任务没有出口，或出口写成「测试通过」这种无法验证的句子。
- 设计不足硬拆：先回退设计，补充组件规格，再回来拆。
- 替开发做实现决定（选哪层、用什么写法）——那是设计的事。
