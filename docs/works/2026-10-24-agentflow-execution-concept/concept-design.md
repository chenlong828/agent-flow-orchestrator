# AgentFlow 执行概念设计与技术支撑点

> 本文是概念验证记录，不是设计规格，也不是实现方案。它只回答：哪些执行概念需要验证、已经定了什么、支撑这些决策的架构方向是什么、边界在哪里。必要的设计决策结论见 §3.2；设计启动输入和待定项见 [`brief.md`](brief.md)；评审结论见 [`result.md`](result.md)。状态机、具体字段、路径等留到设计/实现阶段。

## 1. 目的与范围

### 1.1 要回答的问题

AgentFlow 编排侧要把工作流节点交给 DSH 执行，需要先验证几个技术支撑点是否成立：

- ACP 能否按工作流实例组织进程；
- ACP session 能否作为节点级上下文隔离单位；
- 节点之间能否只通过工作区传递信息；
- Skill 内容与工具能否按节点/专家控制，同时工具仍在本地执行；
- 并发、恢复、评审回退这些执行概念能否落在同一套运行时模型上。

### 1.2 验证对象

1. **实例/进程边界**：一个工作流实例对应一个 ACP 进程，多个实例对应多个进程。
2. **节点/session 边界**：一个可执行节点或 fan-out 子任务对应一个 ACP session。
3. **上下文边界**：节点之间不传对话上下文，只通过工作区传递产物。
4. **供给边界**：Skill 内容由控制面分发，工具在本地执行。
5. **并发边界**：ACP 并发与 Session 并发是两个独立维度。
6. **恢复边界**：中断后直接重跑，不依赖 session 恢复。

### 1.3 前提

- 执行器使用本地 DSH，协议为 ACP；
- 服务端运行时使用 Bun；
- 持久化使用 PostgreSQL（pgsql）；
- 运行在单机开发环境；
- 工作区是节点间唯一的信息通道。

### 1.4 边界

- 不覆盖远程 Harness、多机调度、容器池；
- 不给出生产容量、SLA、性能承诺；
- 不记录排期、验收计划和实现任务；
- 不写数据库表、API、JSON 字段、固定路径、状态字符串等实现细节；
- 本轮没有测试的容量数据不作为结论。

---

## 2. 结论摘要

1. **一个工作流实例绑定一个 ACP 进程。** 多个工作流实例并行时对应多个 ACP 进程；一个进程内可以承载多个 session。
2. **每个可执行节点/子任务新建一个 ACP session，执行完关闭。** 开始、结束、阶段分组、人工确认、fan-in 网关不建 session。
3. **节点之间不传递对话上下文。** 下游节点只通过工作区读取上游产物；评审意见、回退指令、fan-in 报告都经由工作区传递。
4. **Skill 内容由控制面分发，工具在本地执行。** 控制面只做 Skill 正文、工具清单、制品和静态下载，不执行工具。
5. **专家隔离是注意力/逻辑隔离。** 目标是让模型只看到当前节点该用的角色、Skill 和工具，不做 OS 级硬隔离。
6. **服务端运行时使用 Bun，持久化使用 PostgreSQL。** 实例、节点/session 映射、状态和审计记录落库，不只放在进程内存。

## 3. 技术决策

| 编号 | 决策 | 理由与边界 |
|---|---|---|
| D0 | 基础技术栈使用 Bun + PostgreSQL | 编排服务运行于 Bun；工作流定义、实例、节点/session 映射、状态和审计记录落 PostgreSQL；运行时状态不只放在进程内存。 |
| D1 | 执行协议使用 ACP | ACP 支持 per-session MCP、session 关闭和取消，适合按节点组织执行；SDK 模式不作为主方案。 |
| D2 | 一个工作流实例绑定一个 ACP 进程 | 实例级生命周期和故障边界清晰；进程内可复用多个 session，避免按节点或子任务开进程。 |
| D3 | 每个可执行节点/子任务新建 session | session 是上下文隔离单位；评审、回退、重试、重跑都可以用新 session 重新开始。 |
| D4 | 节点间不传对话上下文，只通过工作区传递 | 避免长流程上下文污染；与“工作区是唯一信息通道”的产品模型一致。 |
| D5 | 专家隔离定位为注意力/逻辑隔离 | 目标是让模型聚焦当前节点；共享 workspace、bash、网络是正常工作条件，不承诺对抗性隔离。 |
| D6 | Skill 内容由控制面分发，DSH 原生 Skill catalog 关闭或为空 | 原生 catalog 按 workspace/项目根生效，同一工作区下的 session 会看到并集；控制面可以按 session 控制可见内容。 |
| D7 | 工具在本地 session/workspace 执行 | 工具需要访问代码、临时脚本和本地依赖；控制面只做分发，不进入工具执行链路。 |
| D8 | 工具表按节点/专家控制 | 让模型只看到当前节点该用的工具；同专家 fan-out 共享同一套工具，不重复起工具进程。 |
| D9 | 并发分为 ACP 并发与 Session 并发 | ACP 并发控制活跃工作流实例/进程数；Session 并发控制 fan-out 宽度；非 fan-out 每实例 1 个活跃 session。 |
| D10 | 工作区支持共享、独立、git worktree 三种模式 | 多实例可以共享同一工作区，也可以隔离；worktree 是工作区策略，不改变进程/session 模型。 |
| D11 | 中断/失败恢复采用直接重跑 | 不依赖 session 恢复或历史回放；实例/节点状态落 PostgreSQL，工作区是事实源；恢复时为目标节点新建 session。 |

## 4. 架构方向

### 4.1 实例与进程

```
工作流实例
  └─ ACP 进程（本地 DSH，一个实例一个进程）
       ├─ session：节点 A
       ├─ session：节点 B
       ├─ session：评审节点
       └─ session：fan-out 子任务 1..N
```

- 编排器运行于 Bun；一个工作流实例对应一个 ACP 进程；
- 多个工作流实例并行时，对应多个 ACP 进程；
- 一个进程内可以顺序创建、关闭多个 session；
- 大量 fan-out 子任务表现为 session 序列，不是一子任务一进程；
- 实例、节点/session 映射、状态和审计记录落 PostgreSQL；进程只负责执行；
- 实例完成、失败、终止时，关闭剩余 session 并退出进程。

### 4.2 节点、session 与上下文

- 只有需要 Agent 执行的节点或子任务才建 session；
- 开始、结束、阶段分组、人工确认、fan-in 网关不建 session；
- session 关闭后不复用；节点内部的多轮工具调用在同一个 session 内完成；
- 下游节点不读取上游对话，只读取工作区中声明的产物；
- 评审、回退、人工确认、fan-out/fan-in 的具体流程属于设计层，必要结论见 §3.2。

这些是执行边界，不是节点配置或流程规格。

### 4.3 控制面与执行面

```
控制面：Bun 编排器
  ├─ 实例/节点状态与审计：PostgreSQL
  ├─ 调度、评审判定、回退、人工确认、fan-out/fan-in
  ├─ Skill 正文、工具清单、制品与静态下载
  └─ 工作区登记与审计

执行面：每个工作流实例一个 ACP 进程
  └─ session：可执行节点/子任务
       └─ 本地工具 + workspace
```

- 控制面负责“决定做什么、什么时候做、结果如何判定”；
- 执行面负责“在本地 workspace 里执行节点任务”；
- 控制面不执行工具，不把工具调用收回到服务端；
- 工作区是控制面与执行面之间、节点与节点之间的信息通道；
- 专家隔离是注意力/逻辑隔离，不是 OS 级安全边界。

### 4.4 工作区

- 工作区是节点间唯一信息通道；
- session 的 `cwd` 指向实例或子任务工作区；
- 同一实例内节点共享工作区；
- 多实例可以共享工作区，也可以独立；
- fan-out 子任务按配置使用独立任务目录或 worktree；
- worktree 是工作区策略，不改变 ACP/session 模型；
- 共享工作区时，进程隔离不等于文件隔离；并发写需要锁、路径分区或 worktree；
- 路径声明是契约和审计，不是文件 ACL。

### 4.5 并发

| 维度 | 控制对象 | 说明 |
|---|---|---|
| ACP 并发 | 同时运行的 ACP 进程数 | 即活跃工作流实例数；超出排队 |
| Session 并发 | 单实例 fan-out 时同时运行的 session 数 | 控制 fan-out 宽度；非 fan-out 恒为 1 |

- 非 fan-out 每实例同时只有 1 个活跃 session；
- fan-out 时由 fan-out 宽度限制并发；fan-out 结束后回到 1 个；
- 具体默认值不在本文件确定，见 [`brief.md`](brief.md) 的待定技术问题。

### 4.6 恢复

- 不依赖 session 恢复、历史加载或 transcript 回放；
- 实例/节点状态落 PostgreSQL，工作区是产物事实源；
- 中断/失败后直接重跑目标节点，新建 session；
- 暂停优先在节点边界生效；节点执行中暂停则取消当前 session，恢复时重跑当前节点。

## 5. 关键验证依据与约束

1. ACP `session/new` 只接受一个 `cwd`，不支持 `additionalDirectories`。
2. ACP 支持 per-session MCP；工具表可以按 session 隔离。
3. ACP 支持 session 关闭和取消，不支持加载历史或恢复 transcript。
4. DSH 原生 Skill catalog 按 workspace/项目根生效，不是 session 级；同一 workspace 下的 session 会看到并集。
5. 当前只使用本地 DSH，不涉及远程执行设施。
6. 工具执行在本地；控制面不执行工具，也不提供 `invoke_tool`。
7. 路径声明是契约和审计，不是硬 ACL。
8. 本轮不给出性能或容量结论；开发环境的运行情况不作为生产承诺。

## 7. 术语

| 术语 | 含义 |
|---|---|
| 工作流实例 | 一个工作流模板的一次运行 |
| ACP 进程 | 一个本地 DSH ACP 运行时进程，承载一个工作流实例 |
| session | 一次独立的 Agent 执行上下文；本文中一个可执行节点/子任务对应一个 session |
| 可执行节点 | 需要 Agent 执行的节点；开始、结束、阶段、人工确认、fan-in 不是可执行节点 |
| fan-out | 按清单把一个节点展开为多个子任务 |
| fan-in | 把多个子任务结果聚合为一个结果 |
| fan-out 宽度 | 单实例 fan-out 时同时运行的 session 数 |
| 工作区 | 节点之间唯一的信息通道，也是代码和产物的存放处 |
| worktree | 同一 git 仓库下的独立工作树 |
| Skill 摘要 | 用于 prompt 的简短描述，不是 Skill 全文 |
| 工具表 | 当前 session 可见、可调用的工具集合 |
| 评审回退 | 评审不通过后回到固定目标节点重跑 |
