# 工序：执行面契约 v2（简化版）

## 背景

2026-11-07 冻结的 `executor-http-v1` 是按「exactly-once + 有序控制 + 崩溃补偿」设计的，共 7 个端点、20 条 `SCH`、13 条 `CLT`、1,105 行。2026-11-10 的产品裁决把执行语义重新定为 at-least-once（每个任务最终被下发并跑完即可，允许重复、允许中断后重跑），并指出目标流程只是「任务列表 → 取一条 → 执行 → 回报 → 取下一条」。

此前三轮评审（契约、架构、容错语义）已确认：现行契约中大量机制（`claimRequestId`、尝试租约与 `renew`、`runId` fencing、`late_result`、结果去重、`cleanupPending` 补偿、`assignments` 快照、`pause`/`resume` + `seq`/`ackSeq` 事件流）服务的是「不重复」而不是「跑完」。

**关键时机**：调度器侧对该契约的实现为零（2026-11-10 核实：`src/`、`db/`、`tests/` 无 executor/claim/lease/attempt 任何代码；OpenAPI 31 条 path 中无 `/api/v1/executor/*`；基线迁移无实例/尝试/租约表）。因此现在改契约的成本只落在 client 已有的 5,531 行上，调度器侧没有迁移负担。

## 目标

产出一份**自洽、可直接实现**的 v2 契约，交给 client 侧按其修改，替换 v1。要求：

1. 端点收敛到「取任务 / 交结果 / 取制品」三个；
2. 删掉所有为「不重复」服务的机制，说明删除的理由与被放弃的保证；
3. 保留 at-least-once 下真正需要的：判活、有界终止、结果先落盘、产物保留、并发容量；
4. 给出 v1 → v2 的差异表与 client 改造清单（按组件/文件），client 可直接照单改；
5. 给出桩调度器最小面与验收门禁。

## 范围

- 只定跨进程契约（HTTP 面、语义、职责、错误、容量、超时），不下钻到 client 内部实现。
- 契约权威在调度器侧：本文件即调度器侧的交付物；client 侧的现有 `executor-http-v1.md` 待本版确认后归档。

## 非目标

- 不改 DSH/ACP 行为、不引入新组件。
- 不设计「任务列表」本身（属调度器内部编排状态）。
- 不做观测面（另立 P1）、不做多 client 间的实例迁移。

## 验收标准

| 项 | 判据 |
|---|---|
| 可交付 | client 侧不需要再回看 v1 即可实现；字段无歧义 |
| 可追溯 | 每个被删机制在 §11 有「为什么删」与「删后由什么兜底」 |
| 可验收 | §12 的桩调度器最小面覆盖重复派发、静默回队、超时回队、重复结果 |
| 时机 | 明确「调度器侧尚无实现」，因此不承诺向后兼容 v1 的线上迁移 |
