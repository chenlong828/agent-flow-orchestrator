# 后端契约边界：聚合写与读模型

## 1. 适用边界

**适用**：外部 UI/BFF 的调用形状暴露出后端契约缺口，例如一个保存动作需要多个写端点、列表渲染需要逐个拉详情、BFF 开始编排事务或循环请求。

**不适用**：组件内部实现、纯性能优化、跨聚合的分布式一致性方案选型。组件切分、依赖方向与数据所有权仍按 `arch-design-spec`；本文只处理 UI/BFF 接缝上的契约判定。

本文是方法层的可复用方案，不是当前系统契约。具体端点、字段与错误码以 `design/components/*/spec.md` 为准；两者冲突时，现行规格优先。

## 2. 先看三个信号

| 信号 | 通常意味着 | 先检查 |
|---|---|---|
| 一个用户动作需要调用多个写端点 | 后端缺少聚合写入口，BFF 被迫编排事务 | 这些写入是否属于同一个聚合？ |
| 列表卡片需要显示详情字段，BFF 逐条拉详情 | 列表读模型不完整，或被当成“只有 ID/计数”的索引 | 字段是否稳定、轻量，且是列表主视图所需？ |
| BFF 出现 `for id of ids` 再请求详情，或串行写后补偿 | 后端没有承担应有的读组合或事务 | 能否在 `catalog` 或聚合服务内一次完成？ |

三个信号出现任意一个，先把问题退回后端契约评审；不要在 BFF 里增加业务编排来“抹平”它。

## 3. 写边界

### 3.1 写入口属于聚合，不属于表

- 一个聚合根拥有自己的子表与关联表；同一聚合内的主体、子项、有序关系由该聚合的写入口维护。
- 关联另一聚合时，本聚合只保存目标 ID 与顺序，不接管对方的 CRUD，也不直接读写对方表。
- 目标存在性优先由数据库外键保证；删除保护由 `ReferenceGuard` 一类的端口承担。领域组件不为了校验去调用同层服务。

### 3.2 一个用户动作只产生一个聚合事务

如果 UI 的一个保存动作修改的是同一聚合的主体字段、人设、引用和有序装配：

- 后端提供聚合写入口；
- 根、子表、关联表在同一事务完成；
- `revision` 只递增一次；
- 任一子项失败，整批回滚，不留下半套关系。

不要要求 BFF 串行调用多个领域端点，再用补偿逻辑处理失败。

### 3.3 创建时允许带初始子项

创建聚合时如果 UI 已经选好子项，创建请求应直接接受可选的有序 ID 数组：

- 子项与聚合根同一事务写入；
- 初始 `revision=1`；
- 省略数组表示空装配；
- 目标不存在或重复时整批失败。

“先创建根，再单独装配”可以作为兼容入口保留，但不应成为唯一路径。

### 3.4 部分更新要定义清楚三件事

聚合部分更新至少回答：

1. 字段省略：保持不变，还是回填默认值？默认答案应是**不变**。
2. 数组出现：整体替换，还是增量合并？默认答案应是**整体替换**。
3. 空数组：清空，还是非法？默认答案应是**清空**。

如果一个聚合同时有两类有序关系（例如 Skill 与工具），一次请求应能同时提交两类关系，仍然只递增一次 `revision`。

启停、发布等状态迁移优先保持独立端点；不要为了“少一个接口”把状态语义混进聚合内容更新。

### 3.5 兼容旧入口

聚合写通常是新增能力，不是替换：

- 保留既有的全量更新与单独装配端点；
- 新入口复用同一套领域校验与事务逻辑；
- 旧入口的行为不被新入口悄悄改变；
- 迁移完成前，不要求所有调用方同时切换。

### 3.6 跨聚合不共享数据库事务

同一聚合才共享事务。跨聚合的原子性需求不能靠“把两张表塞进一个事务”解决，应按业务语义选择：

- 外键/引用保护保证引用完整性；
- 失败可接受时，允许分步写入并明确补偿；
- 必须最终一致时，使用 outbox、saga 或对账，不在 BFF 里手写分布式事务。

## 4. 读边界

### 4.1 列表是正式读模型

列表不是详情的索引，也不是“只返回 ID 和计数”的占位符。列表直接服务于选择、导航和卡片渲染，应有稳定、可解释的字段。

### 4.2 列表字段的取舍

| 条件 | 做法 |
|---|---|
| 字段稳定、轻量，列表主视图直接使用 | 放进列表 DTO |
| 关系型数据只需要少量预览 | 在列表项中返回有上限的预览，例如前 3 个 `{id,name}` |
| 字段可选、昂贵、仅部分角色使用 | 才考虑 `include`、独立端点或单独资源 |
| 字段是完整详情或大段文本 | 留在详情，不塞进列表 |

预览要明确：

- 数量上限；
- 排序依据；
- 空集合返回空数组，不返回 `null`；
- 列表预览与详情摘要不是同一载荷，不要为了复用类型把完整摘要塞进列表。

### 4.3 读组合留在后端

跨聚合的读组合由只读目录/读模型承担：

- 领域读契约暴露最小必要数据（例如有序 ID、摘要）；
- 目录组件负责解析名称、分类标签、计数和预览；
- BFF 只做字段映射，不逐条拉详情。

读放大可以接受，但要有边界：列表只取预览所需的少量摘要，详情才取完整装配。规模增长后再评估批量摘要契约，不要提前把批量查询做成默认要求。

### 4.4 字段语义要可验证

新增列表字段时同时写清：

- 来源与派生口径；
- 空值语义（空字符串、空数组还是 `null`）；
- 是否有序、是否唯一；
- 是否只读；
- 详情是否仍是完整版本。

## 5. BFF 边界

BFF 的职责是**适配传输形状**：

- 名称、枚举、分类标签、字段名映射；
- 兼容外部 UI 的历史字段名；
- 不编造业务默认值；
- 不承担多步领域事务；
- 不循环调用领域详情来拼列表；
- 不在 BFF 里实现引用保护、版本递增或装配顺序。

当 BFF 需要“先查 A，再查 B，再合并，再补偿”时，默认判断不是 BFF 需要更多代码，而是后端契约缺少一个业务动作或读模型。

## 6. 反模式

- **BFF 串行写 + 补偿**：三个 `PUT` 依次执行，失败后手工回滚；应由聚合写入口一次完成。
- **列表只给计数，BFF 再拉详情**：列表卡片渲染变成 N+1；应补列表预览。
- **把 `include` 当作主要列表契约**：主视图每次都要的字段，不应要求调用方额外声明。
- **跨聚合共享事务**：把不同聚合的表塞进一个事务，制造隐藏耦合；应按引用/最终一致处理。
- **父组件接管子组件 CRUD**：聚合只保存 ID 和顺序，不复制 Skill/工具的管理职责。
- **详情摘要直接塞进列表**：列表载荷失控；列表只保留有上限的预览。
- **新增字段没有领域含义**：只为一处 UI 临时拼装、无法解释来源与空值语义的字段，不进入公共契约。

## 7. 评审清单

- [ ] 这个动作是否只改一个聚合？如果是，是否只需一次事务、一次 `revision`？
- [ ] 创建路径是否支持初始装配，还是仍要求调用方先创建再装配？
- [ ] 省略、数组替换、空数组清空三种语义是否明确？
- [ ] 旧端点是否保留，行为是否未被悄悄改变？
- [ ] 是否把跨聚合的原子性错误地塞进同一个数据库事务？
- [ ] 列表主视图需要的稳定字段是否已经直接返回？
- [ ] 关系型预览是否设了数量上限和明确排序？
- [ ] BFF 是否仍在循环拉详情、编排事务或编造默认值？
- [ ] 新增字段的来源、空值语义、排序和只读性是否写清？
- [ ] 这条规则是否与现行组件规格冲突？冲突时是否以规格为准？

## 8. 证据与维护

本 playbook 的首批证据来自两个工序：

- [`专家聚合写`](../works/2026-10-25-expert-aggregate-write/result.md)：一个 UI 保存动作原本跨三个写端点；后端补了创建即装配与聚合 PATCH，一次事务、一次 `revision`。
- [`列表读模型补齐`](../works/2026-10-25-list-read-model/result.md)：列表缺少 Skill 触发词、专家 Skill 预览和工具描述；后端直接补列表字段，拒绝 BFF N+1。

维护规则：

- 不写过程叙事、失败流水账或项目专有实现细节；规则要能脱离本次工序复用。
- 不复制端点表、字段表或组件契约；需要时链接现行规格。
- 新规则至少要有一次真实工序证据；只有假设的规则不进入正文。
- `status: draft` 期间允许按新案例修正；经过多次复用后再升为 `current`。
- 废弃时移入 `history/playbooks/`，不从现行文档中保留“半失效”副本。
