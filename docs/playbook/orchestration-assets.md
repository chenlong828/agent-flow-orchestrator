# 工作流编排配置：工作流、专家、技能与工具的配置与管理

## 1 适用边界

**适用**：为一类任务设计新的工作流（功能开发、重构、代码扫描、漏洞检测、审计、运维变更、故障处置等）；新增或调整专家；编写、拆分、升级技能；为节点配置观测与执行工具；评审一套编排配置是否可运行、可复用、可迁移。

**不适用**：具体业务需求的拆解与该领域的验收标准（由对应领域技能定义）；编排引擎的实现细节与接口契约（以组件规格为准）；单个缺陷的修复方法。

本文按“工作形态”而非“研发阶段”组织：功能开发只是变更型工作流的一种，检查型（扫描/审计）与运维型的配置约束不同。

本文是方法层的可复用判断，不是现行系统契约；与组件规格冲突时以规格为准。文中不绑定任何具体项目、语言或框架，示例只保留抽象角色。

## 2 资产模型：四层加运行物

| 层 | 定义 | 变更频率 | 谁维护 |
|---|---|---|---|
| 工作流 | 节点拓扑与回退边；决定“谁在什么时候做什么” | 低 | 流程设计者 |
| 专家 | 人格、职责、验证顺序、注意事项、技能装配；决定“以什么立场做” | 中 | 流程设计者 |
| 技能 | 可复用的判断与步骤；决定“按什么规则做” | 高 | 领域维护者 |
| 工具 | 观测与执行能力（截图、探针、驱动、脚本）；决定“拿什么证据” | 低 | 平台或项目 |

运行物：`run`（一次拓扑执行）、`node`（节点一次访问）、`task`（派发给执行单元的一次任务）、`task-space`（本次运行的过程目录：诉求、各节点产物、证据）。

**分层判据**：一条规则如果只对某个角色成立 → 专家；如果对所有角色都成立 → 技能；如果只对某次运行成立 → task-space；如果决定顺序与回退 → 工作流。

## 3 工作流：拓扑比节点数量重要

### 3.1 设计原则

- **一个节点一件事**。节点职责写不清，说明拆得不对。
- **人工门必须有节点承载**。范围确认、级别确认、结构确认这类“只能由人拍板”的关口，用确认节点表达；靠节点“自觉停手”不可靠。
- **回退边必须指向责任节点**。评审发现的是设计缺陷就回设计节点；只回实现节点会让同一问题在实现层反复修补。
- **验收链要完整**：实现 → 评审 → 测试 → 鉴定 → 收尾。缺一个环节，状态就没有可信的翻转依据。
- **图在运行启动时冻结**。运行中改图不影响在跑的实例；要让新节点生效，必须新起一次运行。

### 3.2 判断一个工作流是否过大

| 信号 | 含义 |
|---|---|
| 单节点预计超过 10 分钟 | 回合数过多，上下文与成本线性上涨 |
| 单节点接近 30 分钟硬超时 | 一次超时就会让整条运行失败，前面的产出作废 |
| 一个节点承载多个可独立验收的交付物 | 应拆成多个任务或多个节点 |
| 回退后总是回到同一个“万能节点” | 拓扑缺责任分层 |

### 3.3 单次运行的范围

一次运行只承担一个可独立验收的交付物。多个交付物塞进一次运行，会让评审一次面对多个提交、失败后回退范围过大、状态翻转失去依据。

### 3.4 工作形态：先分清“改行为、改结构、查事实、动环境”

同一套拓扑原则适用于所有工作，但四类形态的节点链、人工门、证据与失败处理差别很大。配置前先归形态：

| 形态 | 典型任务 | 节点链 | 人工门 | 证据形式 | 失败处理 | 状态对象 |
|---|---|---|---|---|---|---|
| **变更型** | 功能开发、缺陷修复 | 澄清 → 方案 → 评审 → 拆分 → 执行 → 校验 → 收口 | 范围/级别确认 | 测试、截图、差异 | 回退到责任节点 | 需求/场景/任务 |
| **重构型** | 结构优化、迁移、去重 | 基线 → 方案 → 执行 → 行为保持验证 → 收口 | 结构与范围确认 | 前后行为一致（黄金用例）+ 结构指标 | 回退到执行 | 任务/指标 |
| **检查型** | 代码扫描、漏洞检测、合规审计 | 范围与规则确认 → 扫描 → 去伪 → 定级 → 报告 → 收口 | 范围/规则确认；风险接受 | 工具原始输出、复现命令、证据链 | 重扫或复核；不混入“修复” | 发现项（open/confirmed/fixed/waived） |
| **运维型** | 部署、配置变更、故障处置 | 变更申请 → 影响评估 → 执行（可灰度） → 健康校验 → 收口 | 变更窗口与审批 | 命令输出、监控指标、审计日志 | 回滚或降级 | 变更单/事件 |

配置要点：

- **检查型是只读工作流**：不写业务代码，不翻转“已修复”；发现的问题另起修复工作流。扫描结果必须可复现（命令、规则版本、范围），定级需要人工确认阈值与接受策略。
- **运维型按动作风险分级**：R0 只读；R1 可逆（可回滚、可撤销）；R2 不可逆（删除数据、生产变更）。R2 需要明确审批、备份或回滚方案、变更窗口，且执行与验证分节点。
- **重构型的验收是“行为不变”**：先有行为基线，再改结构；结构指标只作辅助，不能替代行为验证。
- **混合任务要拆运行**：例如“扫描 + 修复”“部署 + 回滚演练”，拆成两次运行，各自有独立的评审与收口。

### 3.5 按形态配置资产

| 形态 | 专家侧重 | 技能侧重 | 工具侧重 |
|---|---|---|---|
| 变更型 | 执行者、评审者、校验者 | 需求澄清、方案设计、实现纪律、验收判定 | 测试框架、差异对比、界面观测 |
| 重构型 | 执行者、结构评审者 | 结构规则、迁移步骤、行为保持验证 | 基线用例、结构指标、批量改写 |
| 检查型 | 扫描执行者、去伪判定者、定级者 | 规则解释、误报判定、证据固定、报告格式 | 扫描器、规则集、结果比对 |
| 运维型 | 变更执行者、复核者、值班决策者 | 变更规范、回滚方案、健康判据 | 审计日志、监控指标、灰度控制 |

同一形态内的技术栈差异（语言、框架、平台）只影响**工具技能**，不影响拓扑与公共规则。

## 4 专家：只装“跨技能与流程关键”的规则

### 4.1 字段分工

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 角色 | 一句话定位（做什么、以什么视角） | 方法论步骤 |
| 人格 | 2–3 个形容词 | 与职责无关的偏好 |
| 职责 | 输入、输出、边界 | 具体命令与工具用法（放技能） |
| 验证顺序 | 该角色自检的顺序 | 通用验收标准（放技能） |
| 注意事项 | 该角色特有的禁令与格式要求 | 其他角色也适用的规则（放技能） |
| 技能装配 | 该角色需要的技能 | 把技能内容抄进来 |

### 4.2 装配原则

- 通用规则放技能，专家只放**该角色特有**的约束（例如评审只判定不改状态、收尾只汇总不重跑）。
- 专家不写工作流名、节点名、技能清单；这些由运行注入，写进提示词只会制造耦合。
- 装配不是越少越好，也不是越多越好：**该角色要用到的规则必须能被它读到**。

## 5 技能：最小复用颗粒，必须环境无关

### 5.1 编写原则

- **一类判断一份技能**。技能是“可复用的最小颗粒”，不是章节容器。
- **环境无关**：不写本机路径、项目名、具体命令、语言框架；示例用抽象角色或占位符。
- **一处一事**：同一规则只有一份权威定义。公共规则放共享技能，领域技能引用，不复制。
- **可达性优先**：规则必须出现在“消费方会加载的技能”或“一定会读到的文件”（任务出口、场景卡、交接记录）里。“见某技能”而消费方没装那个技能 = 死指针。
- **可带脚本**：观测/执行类能力可以随技能打包脚本，让技能同时是“说明书 + 工具箱”。

### 5.2 技能分级

| 类型 | 内容 | 例 |
|---|---|---|
| 公共规则技能 | 跨角色共享的元规则（证据分级、边界、状态翻转） | 装到多个专家 |
| 领域方法技能 | 某阶段怎么做（需求、设计、拆分、验证） | 按阶段装配 |
| 专项工具技能 | 某类工具/语言/平台的用法与脚本 | 按技术栈装配 |

### 5.3 版本与分发

- 技能内容变更要升版本；专家装配引用稳定标识。
- 种子数据里，技能与专家可覆盖更新；**工作流只创建不覆盖**（保留界面上的改名与改图）。
- 删除技能前先清装配引用，避免悬挂。

## 6 工具与观测能力：先有工具，再谈验证

### 6.1 缺观测工具的后果

没有标准观测工具时，每个任务会自己写临时探针；同一个“怎么看到结果”的问题被反复重新回答，几轮试错就吃掉一个节点一半的预算。这是运行超时的常见成因，且难以从结果上看出来。

### 6.2 工具契约

| 要素 | 要求 |
|---|---|
| 入口 | 一条命令，参数明确（目标、区域、输出路径） |
| 输出 | 人可读的摘要 + 机器可读的产物（截图、结构化 dump、日志） |
| 判据 | 退出码 + 产物完整性（尺寸、倍率、非空） |
| 边界 | 权限、环境前提、隐私脱敏要求写清楚 |
| 复用 | 工具随技能分发；项目只提供夹具（fixture），不重复实现工具 |

### 6.3 视觉类验证

界面交付的最终形态是屏幕上的样子。标准做法是“运行到确定状态 → 截图 → 直接看图判断”，而不是为每条断言现写探针。截图应通过统一工具一次产出，作为视觉证据；结构性断言再用可重复的 dump 补充。两者一次调用同时产出最省成本。

## 7 证据分级：默认从最轻的开始

| 层级 | 形式 | 成本 | 适用 |
|---|---|---|---|
| L1 | 代码/单元测试 | 秒级 | 默认；逻辑、契约、状态机、错误分支 |
| L2 | 无头探针（编译生产代码后采样/断言） | 分钟级 | L1 观察不到的系统对象、渲染结果 |
| L3 | 标准观测工具截图（可含结构化 dump） | 分钟级 | 视觉正确性、真实界面取证 |
| L4 | GUI 自动化（点击/键盘/辅助功能驱动） | 环境依赖高 | 只有任务出口明确要求且环境具备时 |

规则：

1. 断言必须标层级，不标按最低层处理；
2. 评审不得越级要求；认为层级标低，记建议而不是判失败；
3. L3/L4 由任务出口或验收卡片声明，节点不得自行升级；
4. 任务出口写成自描述形式（层级 + 含义 + 允许改的范围）。

按形态的附加要求：

- **检查型**：证据是“可复现的原始输出”（命令、规则版本、扫描范围），不是摘要结论；每条发现要有定位与复现路径。
- **运维型**：证据是“操作前后对照”（命令输出、监控指标、审计日志），且日志不可篡改；审批记录与执行记录要能对上。
- **重构型**：证据是“行为基线前后一致”，覆盖改动路径的黄金用例 + 全量回归。

## 8 边界与状态

### 8.1 工作区边界

节点的读写范围是本次任务的工作区与过程目录；工作区外的路径不读不写。规则由运行环境注入，不需要去文件系统里搜索定义。确需工作区外的只读信息时，说明理由、最小化读取、记录在案。

### 8.2 越权清单

以下动作不属于普通实现任务，发现即停手并记录：

- 改写设计产物（验收卡片、需求卡片、决策记录、组件规格、排期状态）；
- 自行确认人工门、代写确认记录；
- 发布动作（打包、发布、改版本号）；
- 无审批的破坏性/不可逆操作（删除数据、生产变更、权限调整）；
- 任务出口之外的探针、截图、脚本。

### 8.3 状态翻转

- 实现方只写“建议翻转”与依据，不改最终状态；
- 评审方只出“翻转清单”，不改状态；
- 收尾方在评审通过后统一翻转，并提交一次收口提交（只含状态与证据行）；
- 回退/重跑轮次不得翻转状态。

## 9 运行监控与故障恢复

### 9.1 监控什么

| 观察项 | 正常 | 异常信号 |
|---|---|---|
| 节点耗时 | 单节点 5–10 分钟 | 超过 20 分钟；多次返工同一节点 |
| 回退次数 | 0–2 次 | 同一边反复回退；回退目标不对 |
| 产物 | 各节点产物文件按约定出现 | 节点只改别人的文件、只写结论不落文件 |
| 证据 | 命令输出、截图、dump 可复核 | 只有“我跑过了”的叙述 |
| 工作树 | 收尾后干净 | 长时间脏树；提交混入无关改动 |
| 边界 | 只在工作区内读写 | 读取工作区外路径、翻找规则定义 |

### 9.2 故障处理

- **节点超时**：先看它做到哪一步、产物是否落盘；已提交的成果通常可保留，未提交的进度需要人工判断提交或丢弃。
- **回退上限**：同一节点反复回退到上限会终止运行；出现第二次同向回退时应人工介入，确认是规则问题还是实现问题。
- **运行中改配置**：工作流在启动时冻结，改图要新起运行；技能与专家配置的更新对下一次派发生效。
- **断点续跑**：用新运行承接上一轮的过程目录，明确“复核而非重做”，可把前半程压到几分钟。

### 9.3 运行观测数据（方法层参考，非基准）

以下区间来自单机、单会话的连续运行观测，用于判断量级，不构成 SLA：

| 指标 | 观测区间 | 说明 |
|---|---|---|
| 节点耗时 | 0.1–30 分钟 | 超时上限 30 分钟；超过 20 分钟即高风险 |
| 单节点回合数 | 10–140 回合 | 回合数比耗时更能预测成本 |
| 峰值上下文 | 6 万–27 万 token | 上下文只增不减；长节点会接近窗口的 1/4 |
| 单节点累计输入 | 5 万–2400 万 token | 每轮全量重发，累计量随回合数近似平方增长 |
| 成功运行总时长 | 40–60 分钟 | 单节点峰值通常低于 12 分钟 |
| 失败运行总时长 | 90–130 分钟 | 前置复核约 40%，返工与补证据约 60% |
| 返工占比 | 0–60% | 证据层级失控时返工占比显著上升 |

结论：**成本由回合数决定，回合数由节点范围决定**；控制单节点范围比事后优化更有效。上下文没有自动压缩时，拆节点是唯一可靠的降本手段。

## 10 反模式

| 反模式 | 后果 | 替代 |
|---|---|---|
| 设计节点自建探针/截图 | 设计时间翻倍，挤占实现预算 | 设计只写“接缝待验证”；工具化后由观测工具承担 |
| 每条断言截一张图 | 时间不可控，证据不可复核 | 一次调用产出截图 + dump，按场景引用 |
| 评审要求在卡片之外加证据 | 无限加码，返工循环 | 只按卡片/出口核对；卡外要求记建议 |
| 节点自行确认人工门 | 伪造确认，状态失真 | 人工门用确认节点承载 |
| 实现节点改设计产物 | 设计与实现互相污染 | 越权清单 + 评审直接判失败 |
| 同一产物被两个节点重复产出 | 重复劳动与版本冲突 | 一处一事，明确唯一产出方 |
| 技能写本机路径/项目名 | 换环境即失效 | 抽象角色与占位符 |
| “见某技能”死指针 | 规则实际不可达 | 消费方技能内联，或写入必读文件 |
| 单次运行塞多个交付物 | 评审负担大、回退范围大 | 一个交付物一次运行 |
| 长期无观测工具 | 每个任务重造轮子 | 先把观测工具做成技能资产 |

## 11 配置检查表

### 11.1 新工作流（10 问）

0. 属于哪种形态（变更/重构/检查/运维）？动作风险等级是什么（只读/可逆/不可逆）？
0b. 破坏性操作是否有审批、回滚方案与变更窗口？
1. 一次运行只做一个可独立验收的交付物？
2. 每个节点职责一句话说得清？
3. 人工门有确认节点承载？
4. 回退边指向责任节点？
5. 验收链完整（实现 → 评审 → 测试 → 鉴定 → 收尾）？
6. 单节点预估不超过 10 分钟？
7. 每个节点的产物文件名固定、互不覆盖？
8. 图变更是否需要新起运行，团队是否知情？

### 11.2 新专家（6 问）

1. 角色一句话能说清“做什么、以什么视角”？
2. 职责写了输入/输出/边界？
3. 验证顺序是自检顺序，不是通用验收标准？
4. 注意事项只写该角色特有的禁令？
5. 装配的技能能被它读到，且没有“见某技能”死指针？
6. 没有把工作流名、节点名写进专家？

### 11.3 新技能（7 问）

1. 只做一类判断？
2. 环境无关（无本机路径、项目名、语言框架）？
3. 与已有技能一处一事，没有复制定义？
4. 消费方一定读得到（或已写入必读文件）？
5. 有明确的“何时用/何时不用”？
6. 有可检查的判据（输出、退出码、证据形式）？
7. 需要脚本的，脚本随技能分发；删除时有清理装配引用？

### 11.4 新工具（5 问）

1. 一条命令能跑通，参数明确？
2. 输出既有摘要也有机器可读产物？
3. 失败可区分（权限/环境/输入越界）？
4. 隐私与数据边界写清楚？
5. 项目侧只提供夹具，不重复实现工具？

## 12 与现行文档的关系

- 强制规则应沉淀到技能；本文保留“为什么这样定”和“怎么判断”，不复制技能正文。
- 组件契约与接口以现行规格为准；本文不定义字段、端点与状态机。
- 本文的经验数据来自运行观测，随样本增加更新；更新时保留旧区间以便对照。
