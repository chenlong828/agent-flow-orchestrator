# Skill 包形态 · B1 设计提案

状态：**v1，P1 设计已确认（2026-10-28）；P1 契约已冻结（v1，2026-10-28）。** 本文只写设计层：数据所有权、状态模型、读写路径、契约面、失败与并发语义、存储与重建。字段、操作路径、错误码、表结构、代码落点在契约冻结后再写。整体审视见 [design-review.md](design-review.md)。

审视期间不改本文；如需修改，另起 v2 并记录差异。本次仅更新状态标记，正文未改。

## 0. 一句话

Skill 在 B1 中从“五章结构化子表”变成“一个 zip + 一条 brief”：zip（`SKILL.md` + `scripts/` + `references/`）是内容的唯一真相，数据库只保存列表/检索用的 brief 和管理元数据；编辑期用完整包副本做草稿，保存时重建 `SKILL.md`、打包、原子替换；只提供整包下载。

## 1. 需求边界

| 项 | 结论 |
|---|---|
| 最终形态 | 一个 zip：根 `SKILL.md`，下面 `scripts/`、`references/`；两个目录可为空；无其他根文件或目录 |
| 内容真相 | zip 里的 `SKILL.md`：正文、名称、描述、版本以它为准 |
| 正文分工 | `SKILL.md` 是入口与索引，上限 16 KiB（16384 字节，含 frontmatter）；长文档、脚本、二进制资料放 `references/` 或 `scripts/` |
| 数据库 | 只存 brief（名称、描述、版本、分类、标签、启停、revision、更新时间）与当前包指针；不存正文、不存附件 |
| 编辑 | 服务端草稿目录（完整包副本，含 `SKILL.md`）；单文件上传、改名、删除；草稿跨刷新保留，TTL 24 小时 |
| 保存 | 生成 `SKILL.md` → 与草稿附件一起打包 → 校验 → 原子替换；打包失败即保存失败 |
| 读取 | 列表读 brief；详情与文档解压 zip；文件清单从 zip 解析；只整包下载，无单文件访问 |
| 管理面 | 列表、搜索、分类、标签、启停、删除与引用保护、专家装配不变 |
| 不做 | 版本历史、权限、病毒扫描、运行时执行、单文件访问、附件内联显示、草稿包预览 |

## 2. 关键判断

### 2.1 为什么让 zip 做唯一真相

- 文档输出与下载包必须逐字一致；如果正文另存一份，就有两个真相，迟早漂移。
- 代价：详情和文档要解压；列表仍走 brief，不受影响。
- 否决：数据库存正文 + 保存时生成 zip（两份，需同步）；也否决文档端点现场拼装（与包可能不一致）。

### 2.2 为什么草稿是完整包副本

- 用户要按文件管理附件，且刷新后不能丢；草稿必须是服务端可继续操作的包副本。
- 代价：进入编辑要解压一次；磁盘占用；过期清理。
- 否决：客户端清单（刷新丢、页面承担组装）；整包上传（改一个脚本要重传整个包）；无草稿（附件在保存前无处安放）。

### 2.3 为什么保存时打包、失败即失败

- 包是保存结果的一部分；如果保存成功但包没生成，就出现“正文已生效、下载物不可用”的半状态。
- 代价：保存要等打包；大包慢。草稿保留，可重试。
- 否决：保存成功、下载时再打包（下载路径要处理失败与重建，且与“包是唯一真相”冲突）。

### 2.4 为什么不做单文件访问

- 附件是脚本或二进制资料，不是页面内容；只下载整包足够。
- 收益：不暴露单文件读取面，不需要内联 MIME 策略，攻击面最小。
- 代价：页面只能看文件名与大小，不能单文件核对。

### 2.5 为什么分类、标签、启停留在数据库

- 它们是管理面元数据，不是 Skill 包的内容；zip 是可移植的运行时资料。
- `SKILL.md` 的 frontmatter 只放 name、description、version。
- 列表与检索依赖 brief，不依赖解压。

### 2.6 为什么 SKILL.md 只留入口

- 16 KiB 上限强制把长文档、长脚本移到 `references/` 或 `scripts/`；`SKILL.md` 只负责触发说明、步骤索引和引用清单。
- 代价：编辑者要主动拆分内容；收益：加载快、包结构清楚，避免正文变成难以维护的长文。
- 否决：不设上限或放宽到数百 KiB（正文与附件的边界消失，详情解压和渲染变重）。

## 3. 组件与数据所有权

| 组件 | 职责 | 数据/资源 | 不负责 |
|---|---|---|---|
| `CMP-skill` | Skill 包生命周期：brief、草稿、保存、读取、GC 编排 | brief、管理元数据、草稿记录、当前包指针；经存储端口读写包与草稿目录 | HTTP、跨资产装配、UI |
| `CMP-platform` | 文件存储适配：原子写、读、删、列目录、临时区 | 存储根下的包、草稿、临时文件 | 业务规则、状态机、路径语义 |
| `CMP-config` | 存储根、TTL 与限额等启动配置 | 无持久化 | 业务规则 |
| `CMP-kernel` | 存储端口与共享错误词汇 | 无 | 实现 |
| `CMP-catalog` | 列表、详情、文档、文件清单的读模型组合 | 无 | 写、存储 |
| `CMP-http-gateway` | 协议翻译：multipart、下载头、错误映射 | 无 | 业务规则 |

- 不新增业务组件；`CMP-skill` 内部分为“包构建、草稿、读取”三个模块，超出尺寸预算再拆。
- 包与草稿的字节归 `CMP-skill` 所有，`CMP-platform` 只是适配器；其他组件不得直接读存储根。
- 数据库 brief 与包指针由 `CMP-skill` 唯一写入；`CMP-catalog` 只读。
- 现有 `CMP-skill` 规格约 9 KB，新增设计后仍在 120 KB 预算内；实现阶段若超，拆内部模块而不是新增组件。

## 4. 状态模型

```text
(无) --新建草稿--> 草稿 --保存成功--> 已保存
已保存 --进入编辑--> 草稿 --保存成功--> 已保存
草稿 --取消或过期--> (无)
已保存 --删除--> (无)
```

不变量：

- 草稿对列表、详情、文档、整包下载不可见。
- 已保存的包按 revision 不可变；保存生成新 revision 的包，成功后切换当前包指针。
- 草稿记录保存 base revision 与 base version；保存时 revision 不一致即拒绝，不消费草稿。
- 保存成功 = brief、当前包指针、revision、草稿消费在同一事务；失败则旧包与旧 brief 不变，草稿保留。
- 一个草稿只能被一次成功保存消费；重复保存请求按 revision 冲突拒绝。
- 已保存 Skill 删除时，包与草稿一并清理；引用保护仍先执行。
- 允许多个草稿并存（多标签页、多人），各自带 base revision；后保存者冲突。

草稿记录的设计级字段：草稿标识、所属 Skill（新建时为空）、base revision、base version、创建时间、过期时间、操作者展示名。草稿目录按草稿标识定位。

## 5. 读路径

| 读 | 数据来源 | 行为 | 失败 |
|---|---|---|---|
| 列表与检索 | 数据库 brief | 不碰 zip；返回名称、描述、分类、标签、启停、revision、更新时间 | 数据库不可用则整体不可用 |
| 详情 | zip + brief | 只读 zip 中央目录与 `SKILL.md` 条目，取 name、description、version、正文；文件清单来自目录；brief 补分类、标签、启停、时间 | zip 缺失或损坏时明确报错，不回落 brief 正文 |
| 文档 | zip | 只读 `SKILL.md` 条目并原样返回；ETag 用 revision；条件请求命中则空响应 | 同上 |
| 文件清单 | zip 目录 | 只读路径与大小；含只读 `SKILL.md` 条目；不读文件内容 | 同上 |
| 整包下载 | zip | 返回已保存包；按附件设置下载文件名；停用可读 | 包缺失时报错 |
| 草稿文件清单 | 草稿目录 | 编辑页使用；含只读 `SKILL.md`；不返回正文 | 草稿过期时报错 |

- 详情与文档只读 zip 中央目录与所需条目，不整包解压；是否缓存按实测再定，缓存键为 revision，不作为首版必需。
- 详情正文为 `SKILL.md` 去掉 frontmatter 后的内容；文档返回整份 `SKILL.md`。
- 文件清单只给元信息，不提供单文件读取。
- 详情与文档的名称、描述、版本以 zip 的 frontmatter 为准；列表的对应字段是 brief 投影。
- 搜索只覆盖 brief 的 name/description；不搜正文、不搜 `references/`。
- brief 与 zip 的 name/description/version 是投影关系；只有保存写两者；不自动修复，作为排障项。

## 6. 写路径

### 6.1 进入编辑

- 已保存 Skill：创建草稿记录（base revision 与 base version），把当前包解压到草稿目录，形成完整副本（含 `SKILL.md`）。
- 新建：创建空草稿目录；保存时才建 Skill。
- 草稿跨刷新保留；TTL 24 小时；取消即删。
- `SKILL.md` 在草稿里存在，但不在附件管理面：不能上传、改名、删除；保存时用新生成内容覆盖。

### 6.2 附件操作

- 上传、改名、删除只作用于草稿目录；不推进 revision 与 version，不影响已保存包。
- 校验：只允许 `scripts/`、`references/` 根，允许子目录；单文件 20 MiB、100 个文件、单包 100 MiB；拒绝绝对路径、`..`、`.`、空段、反斜杠、控制字符、结尾 `/`，以及把 `SKILL.md` 作为附件路径。
- 同路径上传覆盖；改名到已存在路径冲突；大小写与 Unicode 归一化按存储原样，具体在契约冻结时写清。
- 空目录可以不写入包；没有附件时包内只有 `SKILL.md`。

### 6.3 保存

1. 取草稿；校验未过期；校验 base revision 与当前 revision 一致。
2. 校验草稿文件集：路径、数量、总量、无符号链接。
3. 计算新 version，生成 `SKILL.md`（frontmatter + 正文）；按最终 UTF-8 字节数计（含 frontmatter），上限 16 KiB（16384 字节）；超出则保存失败，提示把长内容移到 `references/`。
4. 在临时区打包成新 zip；校验条目；写到存储根的新包文件（唯一文件名），fsync 文件与目录。
5. 数据库事务：更新 brief、当前包指针、revision、更新时间；消费草稿。
6. 提交后删除草稿目录；旧包按 GC 策略清理。
7. 任一步失败：删除临时文件与新包；旧包与 brief 不变；草稿保留；返回错误。

补充：

- 新包使用唯一文件名，数据库保存当前包指针；不按 revision 推导路径，避免并发保存在同一路径互相覆盖。
- 新建时在第 5 步插入 Skill 记录，并做名称唯一校验。
- 名称、描述、分类、标签、启停的修改与包在同一次保存中提交；启停单独修改不重建包。
- 16 KiB 错误带 `limitBytes` 与 `actualBytes`，并指向正文；展示端显示字节计数，服务端是最终裁判。
- 包文件 fsync 失败：保存失败，旧包与 brief 不变，草稿保留。
- 数据库提交失败：删除新包；旧包与 brief 不变；草稿保留。
- 保存响应丢失时，重试会因 revision 已变而冲突；调用方重新读取确认即可，不会重复写。
- 同一草稿并发保存以 revision 与草稿消费为闸门，只有一次成功。

### 6.4 取消、过期、删除

- 取消：删草稿记录与目录。
- 过期：TTL 清理；已上传附件一并删除。
- 删除 Skill：先引用保护；再删 brief、包、草稿；失败由 GC 兜底。

### 6.5 失败语义

| 失败点 | 结果 |
|---|---|
| 草稿过期 | 保存失败；草稿不可恢复；提示重新进入编辑 |
| revision 冲突 | 保存失败；草稿保留；不覆盖 |
| 路径或限额校验失败 | 保存失败；草稿保留；指出具体文件 |
| `SKILL.md` 生成失败 | 保存失败；旧包不变；草稿保留 |
| 打包失败 | 保存失败；旧包不变；草稿保留 |
| 包文件写入失败 | 保存失败；临时文件清理；草稿保留 |
| 数据库事务失败 | 保存失败；新包删除；旧包与 brief 不变；草稿保留 |
| 提交后删旧包失败 | 保存成功；旧包成为孤儿，由 GC 清理 |
| 提交后删草稿目录失败 | 保存成功；草稿目录由 GC 清理 |

## 7. 存储与运维

- 存储根可配置，默认本地目录；包、草稿、临时区分离。
- 设计级布局：每个 Skill 的包放在自己的目录下，文件名唯一；每个草稿一个目录；临时区用于构建。
- 原子写：先写临时文件，fsync 文件，rename 到目标，fsync 目录，再提交数据库；失败清理。
- 崩溃窗口：临时文件、已 rename 未提交、已提交未删旧包、已提交未删草稿；启动与周期 GC 对账。
- 备份：开发库可重建，不要求备份；若保留演示数据，自行备份数据库与存储根。
- GC：过期草稿、被替换的旧包、临时文件；单实例执行；启动时与周期执行；失败重试。只删非当前指针的包，并留 grace period，避免删掉正在构建或下载的文件。
- 磁盘：单 Skill 100 MiB 上限；全局用量监控；磁盘满时保存失败、草稿保留。
- 观测：保存、打包、草稿、GC 的成功失败计数与耗时，存储用量；日志带 Skill 与草稿标识，不含文件内容。

## 8. 安全与限制

- 包由服务端构建，不接受任意 zip 上传；仍校验条目名、大小、数量与符号链接。
- 只整包下载，不内联、不单文件读取；下载按附件处理。
- 附件是不可信内容；运行时执行需自行隔离，B1 不扫描、不执行。
- 路径限制见 6.2；zip 条目不允许 `..`、绝对路径、控制字符。
- 无鉴权；操作者头只用于展示，不构成草稿所有权；草稿标识本身是 bearer capability，拿到即可读写。单机本地原型接受此限制，对外必须加鉴权。
- 下载头的文件名要清洗引号、CRLF 与路径分隔符；`SKILL.md` 里的原始 HTML/JS 由展示端 sanitize，B1 只返回 `text/markdown`。
- 限额：单文件 20 MiB、100 个文件、100 MiB 每包；`SKILL.md` 16 KiB（16384 字节，含 frontmatter），长内容放 `references/`。
- 文件名允许 Unicode，但拒绝控制字符与路径分隔符歧义；具体字符集在契约冻结时定。

## 9. 迁移与兼容

- 决定：无生产使用，当前 Skill 都是演示数据；不做升级迁移、不回填、不保留旧 Skill 数据，开发库原地重建。
- 重建：drop/recreate 开发库 → 按新 schema 建 → seed 重建 12 个 Skill 的包与专家装配边；旧五章、踩坑、引用子表与字段不再存在。
- “不迁移”的边界：不承担旧库升级与旧数据保留；schema 变更仍要按 migrator 的约束落成 fresh-only 基线（只服务空库），不改变“无升级路径”的结论。
- 旧 `skill` 行、`expert_skill` 边、三张子表随重建消失；不处理 `on delete restrict` 的升级顺序，因为不做原地升级。
- 种子必须为每个 Skill 生成合法 zip 与 `package_key`，并校验 16 KiB；测试的表清单、迁移版本、清理表同步为重建后的结构。
- 破坏性契约：单消费方、无生产数据，不做 `/api/v2`；在 `history/decisions/` 记录例外。
- 契约权威在 B1；UI 侧 2026-10-27 提案作为输入，其中 `body` + staging 部分被本设计取代，契约冻结后 UI 同步。
- B1 规格同步：skill、catalog、http-gateway、platform、config、architecture；种子、测试同步。
- 回滚：没有旧数据可回滚；开发库可再次 drop/recreate，包与草稿目录在重建时清空。

## 10. 定级与确认门

**P1**：核心契约、核心 schema、数据所有权（包、草稿、存储端口）、跨项目消费方。

人工门：

1. 本设计确认：数据所有权、状态模型、读写路径、失败与并发语义。
2. 契约冻结：字段、操作、错误、ETag、限额。
3. 开发库重建步骤确认后执行；无升级迁移、无数据保留。

## 11. 验证计划

- 契约：列表、详情、文档、文件清单、整包下载、新建、更新、草稿上传、改名、删除、取消、保存。
- 状态：草稿生命周期、保存成功、取消、过期、revision 冲突、重复保存、打包失败、数据库失败；上传覆盖与改名冲突。
- 数据：保存后 brief 与 zip 的 name、description、version 一致；列表走 brief；详情与文档走 zip；无第二份正文；搜索只覆盖 brief。
- 存储：fsync 顺序、崩溃窗口、原子替换、旧包清理、缺失或损坏包、孤儿包、GC；开发库可重建，不要求备份恢复。
- 安全：路径穿越、超限、符号链接、单文件访问不可用、下载头文件名清洗、Markdown 由展示端 sanitize、草稿标识能力边界。
- 重建：drop/recreate 后新 schema 正确，旧表不存在；seed 重建 12 个 Skill 的包与装配边；测试表清单与迁移版本同步。
- 正文边界：`SKILL.md` 16 KiB 按最终 UTF-8 字节计（含 frontmatter），超限保存失败并提示 `references/`；长内容放附件不挤占正文。
