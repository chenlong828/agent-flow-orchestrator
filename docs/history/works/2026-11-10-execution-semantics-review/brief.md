# 工序：执行容错语义提议评审（fan-out / 卡死处理）

## 背景

client 侧提交《提议：Agent 执行任务的容错语义与卡死处理》（`agent-flow-client/docs/history/works/2026-11-10-execution-semantics-proposal/proposal.md`，2026-11-10），请调度器侧裁决 §9 的 Q1–Q8。

产品前提已在对话中明确：client 跑的是 **Agent 智能体分析任务**，容错大——中断后工作区留有中间分析与知识落盘，重跑时 agent 能读到痕迹并自行决定续跑或重来。因此调度器的重点是**安排活儿**（派发、容量、卡死回收、重试节奏），而不是交易类系统的 exactly-once。这一定性构成本次评审的判据。

## 目标

1. 按上述产品前提判断提案的语义重排是否成立，指出哪些「强一致」要求该降级、哪些不能降。
2. 逐条答复 Q1–Q8，给出调度器侧的采纳结论与需要补的字段。
3. 指出提案自述「契约只加一个可选字段」是否成立，以及不成立时的最小加法。

## 范围

- 只评语义、职责边界与契约影响；不评 client 内部实现结构（S1/S2 已落地的代码只作证据核对）。
- 契约现状以 `agent-flow-client/docs/design/contracts/executor-http-v1.md`（v1 frozen）为准。

## 非目标

- 不设计 B 方案（fan-out 真并发）的仓库级冲突策略（Q8 已定另立 P1）。
- 不评 idle 看门狗的具体实现（计时器、事件源），只评它的语义位置与默认值风险。

## 验收标准

| 项 | 判据 |
|---|---|
| 逐条答复 | Q1–Q8 每条有采纳/否决/改法，注明落在契约还是调度器文档 |
| 契约影响 | 明确指出提案遗漏的加法项，说明不加会怎样 |
| 证据 | 每条结论能指到契约条款或代码位置 |
