# 对照：现行实现 vs「任务列表 + 逐条下发」

> 依据：`agent-flow-client` 当前实现（`src/` 5,531 行，S1/S2 已落地）与冻结契约 `docs/design/contracts/executor-http-v1.md`（1,105 行）。
> 目标流程（用户 2026-11-10 给出）：
> 1. fan-out 前由上一节点规划出任务列表（几十到上千）；
> 2. 取一个任务，任务信息作为参数 + fan-out 的 expert 组合 → 一个 session 执行；
> 3. 按并发下发多个任务到 client 并发执行；
> 4. 某任务完成 → 回报 result → 列表不空则取下一个。
>
> 明确前提：执行过程可中断（该任务算没跑完），**只要最终每个任务都被下发并跑完即可**；不考虑并发冲突。

## 1. 先把目标流程翻译成协议形状

| 你的步骤 | 需要的机制 | 现在由什么承担 |
|---|---|---|
| 1 任务列表 | **纯调度器内部状态**（queued / running / done），不进契约 | 调度器侧（本仓库，尚未实现） |
| 2 取任务 + expert 组合 → session | 一个「给我活儿」的请求 + 技能集下发 | `C-03` claim（含 `claimRequestId`、租约）+ `C-04` bindSession + `C-05` 下载 |
| 3 按并发下发 | 一个「还能接几个」的数字 | `SCH-19`（同实例单 attempt）+ 容量 `availableInstances` + 实例锁 |
| 4 回报 + 取下一条 | 一个「交差」的请求 | `C-07` reportResult（含幂等、`disposition`、`late_result`） |
| — | 判活 + 兜底终止 | `C-02` 心跳长轮询 + 客户端租约；`C-06` 续租 + 尝试租约；`timeoutMs` |

**关键差异**：你的目标函数是「每个任务最终跑完」（at-least-once）；现行契约的隐含目标是「每个任务只跑一次、控制事件有序可靠、崩溃后状态可补偿」（exactly-once + ordered）。下面 90% 的多余机制都来自这个差异。

## 2. 按「它防的是什么」分三类

| 类 | 防的事 | 与你的场景 | 处置 |
|---|---|---|---|
| A | 任务永远跑不完（卡死、进程残留） | 真实存在，是这个流程的主要风险 | **必须留** |
| B | 同一个任务跑两次 | 你的场景里可接受：产物在、agent 能识别痕迹，代价是 token | **可整体删** |
| C | 存储/协议本身出错（损坏、乱序、版本漂移） | 单机 + 双端自研，概率极低 | **可大幅简化** |

现行实现里，B 类占了契约的大头，也是实现里最绕的部分。

## 3. B 类：为「不重复」付出的机制

| # | 机制 | 出处 | 它防的事 | 你的流程里会发生吗 | 删掉后的代价 |
|---|---|---|---|---|---|
| 1 | `claimRequestId` 幂等键 | 契约 §5.3；`gateway/state.ts` `ClaimIdempotency` | 响应丢失导致同一请求领到两个任务 | 会丢响应，但多领一个任务 = 白跑一次分析 | 无（最多多跑一次） |
| 2 | `renew` + 尝试租约（TTL/3、120s） | 契约 §5.6；`gateway/state.ts` `LeaseTracker` | 长任务期间「这活儿还是不是我的」 | 只有「不重派」时才需要；你允许重派 | 判活少一层（见 §4：客户端租约仍留） |
| 3 | `runId` fencing + `run_superseded` + 退出码 7 | 契约 §5.1、`SCH-02`；`serve-loops.ts` 4 处 | 同一 `clientId` 双开两个进程同时领活 | 单机单进程部署下几乎不发生；发生了也只是重复分析 | 双开时两个都跑，结果取最后一次 |
| 4 | `late_result`（409，只审计） | 契约 §5.7；`gateway.ts:229` | 旧 attempt 的结果覆盖新 attempt | 中断的任务结果本来就没价值 | 结果按 `attemptNo` 取最大即可，不需要专门错误码 |
| 5 | 结果去重（`IdempotencyCache` 256 条 + `disposition=duplicate`） | 契约 §4.5；`gateway/state.ts` | 客户端重试上报导致重复入库 | 重复上报只会多写一条 | 服务端按 `taskId` 覆盖写 |
| 6 | `cleanupPending` / `cleanupAcks` / `releaseId` / `SCH-20` | 契约 §5.1.5、§5.2、`SCH-20`；`executor.reconcileCleanup`、`serve.ts:52`、`serve-events.ts:26/76`、`run.ts:58` | 释放/清理意图随旧 run 事件丢失 | 你的模型里**没有「释放实例」这个动作**——一个 fan-out 跑完就完了，容器默认保留 | 清理变成运维脚本按 `instanceId` 删目录 |
| 7 | `assignments` / `assignmentsVersion` 快照 | 契约 §5.1.4；`serve-context.ts` 仅回传 | 重启后校验容器归属 | client 自己有 journal 与目录 | 无 |
| 8 | `pause` / `resume` + `seq`/`ackSeq`/补发/空洞 | 契约 §5.2、`SCH-08`；`gateway/state.ts` `ControlSeq` | 控制指令有序、至少一次、断连补发 | 暂停 = 调度器不下发即可；停止 = 下发一次停止 | 见 §5：换成状态位 |
| 9 | 7 态状态机 + `settled`/`reported` 分离 + `abandoned` | 契约 §9；`executor/executor.ts` | 崩溃后区分「有结果没报」与「没跑完」 | 有结果没报 → 重报比重跑便宜，这个**值得留**；但不需要 7 个状态 | 简化为 `running` / `done` / `failed` |
| 10 | journal 压缩/损坏降级/`corrupt` | 契约与 `store/journal.ts` | 存储介质出错 | 单机本地文件，概率极低 | 启动时忽略坏行即可 |
| 11 | `compatibility` / `deprecated` / `sunsetAt` / 426 | 契约 §12 | 多版本共存与废弃窗口 | 双端同仓发布 | 用一个整数版本，不等就退出 |

## 4. C 类：可以简化但不该删的

| 机制 | 简化后 |
|---|---|
| 双租约（客户端 90s + 尝试 120s + `renew`） | **只留客户端租约**：一个「取任务」的长轮询连接本身就是判活信号；连接断了/超时了，调度器把该 client 已下发未结算的任务放回队列。尝试租约与 `renew` 是同一件事的第二层计时 |
| 心跳与领取两条长轮询 | 合并为一条：空闲时挂着等任务，返回任务或空。忙时任务已下发、尚未回报，调度器按「已下发未回报 + 超时」判断，不需要第二条连接 |
| `serverTime` + 单调时钟 + ±5s 容忍 | 同机场景本地时钟足够；只保留 `timeoutMs` |
| `429` / `Retry-After` / `maxRequestBytes` | 单 client 单机，删 |
| `X-Request-Id` 回显 + 审计关联 | 留（几乎零成本，排障有用） |
| 技能集 digest 冲突守卫（`asset_skill_set_conflict`） | 同一 fan-out 所有任务同一 expert、同一技能集，冲突不会发生；去掉检测，只留「同 digest 幂等短路」 |

## 5. 结构性建议：把「事件流」换成「状态同步」

这是复杂度最大的单点，且不属于 B 类而是协议形状问题：

- **现在**：控制事件是 edge-triggered——每条指令有 `seq` 序号、按 run 单调、至少一次投递、断连补发、`ackSeq` 累计确认、`issuedAt` 作用域判定。这套东西的正确性论证与实现（`ControlSeq`、`SCH-08`、§5.2 的 106 行）在消息队列里才值得。
- **改成**：level-triggered——任何时候，调度器都只是「告诉 client 当前期望状态」（`run` / `hold` / `stop`）。client 收到就收敛到那个状态，丢一条下一条还会带同样的状态，所以不需要序号、不需要补发、不需要 ack。

收益：删掉 `seq`/`ackSeq`/补发窗口/`issuedAt` 作用域/4 个控制事件，`pause`/`resume` 退化成「调度器不下发」。

## 7. 不能删的（防止简化过头）

1. **一层判活**：连接或心跳，二者留一个。否则 client 死了，任务永远卡在 running。
2. **`timeoutMs` + 进程组回收**：这是「任务跑不完」的唯一兜底，也是你这个流程最需要的东西（上千个任务里一个 hung 就会堵住队列）。
3. **结果落盘再上报**：重报比重跑便宜一个数量级的 token。值得留一层「有结果没报」的记录。
4. **产物保留（`keep`）**：这是「重跑能识别痕迹」的前提。
5. **结果大小上限与截断**：防止单条结果撑爆传输。
6. **同实例单写者**：一个实例同一时刻一个 attempt。你的流程里它就是「一个 session」，保留即可，不需要升级成写域/隔离那套。
7. **孤儿进程清理**：可简化成「启动时按 pgid 清掉上次残留」，不需要 `OrphanRecord` 文件与 `listOrphans/clearOrphan` 这套接口。

## 8. 处置建议（契约已冻结、代码已落）

不建议重写，按「不再新增 → 逐项裁剪」推进，顺序：

1. **先删死代码**：`renew`/`LeaseTracker`（契约有、CLI 循环未接线）、`IdempotencyCache`（只在进程内去重，单流水线无意义）、`assignments` 回传（无消费者）。
2. **再删无收益的协议**：`claimRequestId`、`late_result`、`run_superseded` 与退出码 7、`pause`/`resume` + `seq` 体系。
3. **最后动结构**：双租约合并为一层、`cleanupPending` 整块移除、两条长轮询合并。

第 1、2 步只删不加，不触发契约版本升级的必要性论证；第 3 步属 P1，建议与 B 方案（并发）一起做。
