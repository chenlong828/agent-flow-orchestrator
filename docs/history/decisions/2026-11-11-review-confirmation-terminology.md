# 2026-11-11 评审确认术语：统一为「人工评审确认」

## 背景

技能与历史工序用「人工确认门」「人工门」「确认门」指 P0–P3 改动级别里由人做确认的那一步。这套写法是 2026-10-23 从上游 `~/skills/af-dev-skill` v0.1 复制进来的，不是行业通用词；「人工门」还是在「人工确认门」基础上再压缩的缩写。用户 2026-11-11 指出这是自造词，要求统一为**人工评审确认**，并明确技能本身要改、历史文档一并改。

## 决策

1. **术语统一**：所有表示该确认环节的「人工确认门」「人工门」「确认门」改为「人工评审确认」；保留「第一道 / 第二道」这类序数表达。
2. **改本地技能**：修改 `.agents/skills/` 下 `arch-design-spec`、`design-before-coding`、`dev-execution-spec` 三个技能正文，与上游 `~/skills/af-dev-skill` v0.1 分叉；这是本地第二处与上游的差异，第一处是 2026-10-29 的「评审四档裁决」。
3. **历史文档一并改**：`docs/history/works/` 下引用旧词的工序文档按用户明确要求同步替换。历史目录「冻结只读」的规则本次按用户授权例外处理，只替换术语，不改结论、事实、时间线与文档状态。
4. **不改领域内的「人工确认」**：`confirm` 节点语义（人工确认节点、人工确认不建 session、等待人工确认状态）指工作流节点，不是评审确认环节，保持原词。
5. **不改上游**：`~/skills/af-dev-skill` 仍是 v0.1，本次只改本仓库副本；`AGENTS.md` 已登记该分叉。

## 被否决的方案

- **只改当前文档、不改技能**：技能是后续工序的规范来源，不改会继续产出旧词；用户也明确要求改技能。
- **直接改上游 `~/skills/af-dev-skill`**：上游是只读副本，升级方式是覆盖；本地分叉 + 决策记录是本项目既有做法。
- **用「评审门禁」「阶段门」「审批关卡」替代**：这些是行业通用词，但用户选定「人工评审确认」，以用户选择为准。
- **把领域内的「人工确认」一起改**：会把 `confirm` 节点语义与评审确认混为一谈，导致节点规格与契约歧义。

## 后果与回滚

- 本地技能与上游分叉第二处；下次覆盖升级前必须 diff 核对「四档裁决」与「术语」两处改动是否已回灌。
- 历史文档的二级标题改名后，中文锚点随之变化；已检查仓库内没有跨文档链接指向这些旧标题，`docs:check` 通过。
- 回灌方式：上游升 v0.2 时合入三处技能 diff 与该术语；回滚方式为恢复旧词并删除本条记录。
- 本次不改代码、端点、表或迁移。
